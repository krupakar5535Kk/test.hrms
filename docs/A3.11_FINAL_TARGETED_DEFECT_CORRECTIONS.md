## 3. FINDING A — PAYROLL SNAPSHOT AND FREEZE INTEGRITY

### 3.1 Exhaustive Inventory of the 11 Payroll-Affecting Sources
A payroll freeze must prevent retrospective modifications to any data point that contributed to the financial calculation of a closed or frozen period. The 11 source tables are:

1. `attendance_days` (Root daily aggregate: work duration, attendance status, lock status)
2. `attendance_punches` (Child event of `attendance_days`: punch timestamps, raw device inputs)
3. `overtime_allocations` (Child event of `attendance_days`: approved daily OT minutes/tiers)
4. `leave_requests` (Employee date-range leave booking impacting daily status)
5. `leave_balances` (Employee period/annual balance ledger impacting paid vs unpaid leave)
6. `salary_assignments` (Employee compensation structure, hourly rates, allowances)
7. `shift_assignments` (Employee shift schedule determining expected work hours)
8. `holidays` (Organization-wide calendar overrides impacting work expectations)
9. `payroll_adjustments` (Manual period-specific financial credits/debits)
10. `attendance_audit_logs` (Audit corrections and manual overrides to attendance)
11. `payroll_period_overrides` (Ad-hoc overrides to period calculation parameters)

### 3.2 Freeze Guard Trigger Specifications & Complete Source Code
All freeze guards must execute `BEFORE INSERT OR UPDATE OR DELETE` at row level.
- **INSERT:** Verifies that `NEW.work_date` (or resolved parent date) does not fall within a `FROZEN` or `CLOSED` payroll period.
- **DELETE:** Verifies that `OLD.work_date` does not fall within a `FROZEN` or `CLOSED` payroll period.
- **UPDATE:** **Must inspect BOTH `OLD` and `NEW` records.** If the row previously belonged to a frozen period, modifying it is prohibited. If the modification attempts to move the row into a frozen period, it is prohibited.

```sql
-- ============================================================================
-- HELPER: Resolve Payroll Period Status by Organization and Date
-- ============================================================================
CREATE OR REPLACE FUNCTION public.fn_assert_period_not_frozen(
  p_organization_id UUID,
  p_target_date DATE,
  p_operation TEXT,
  p_table_name TEXT
) RETURNS VOID
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, public
AS $$
DECLARE
  v_period_record RECORD;
BEGIN
  -- Look up any payroll period covering the target date
  SELECT id, period_name, status
  INTO v_period_record
  FROM public.payroll_periods
  WHERE organization_id = p_organization_id
    AND p_target_date BETWEEN start_date AND end_date
  LIMIT 1;

  IF FOUND THEN
    IF v_period_record.status IN ('FROZEN', 'CLOSED', 'ARCHIVED') THEN
      RAISE EXCEPTION 'Payroll freeze violation on table % during %: Target date % falls in % period % (ID: %)',
        p_table_name, p_operation, p_target_date, v_period_record.status, v_period_record.period_name, v_period_record.id
        USING ERRCODE = '55000'; -- object_not_in_prerequisite_state
    END IF;
  END IF;
END;
$$;

-- ============================================================================
-- 1. attendance_days Freeze Guard
-- ============================================================================
CREATE OR REPLACE FUNCTION public.fn_freeze_guard_attendance_days()
RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, public
AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    PERFORM public.fn_assert_period_not_frozen(NEW.organization_id, NEW.work_date, TG_OP, 'attendance_days');
    RETURN NEW;
  ELSIF TG_OP = 'UPDATE' THEN
    -- Check old date/org
    PERFORM public.fn_assert_period_not_frozen(OLD.organization_id, OLD.work_date, TG_OP, 'attendance_days');
    -- Check new date/org if changed
    IF (NEW.work_date <> OLD.work_date) OR (NEW.organization_id <> OLD.organization_id) THEN
      PERFORM public.fn_assert_period_not_frozen(NEW.organization_id, NEW.work_date, TG_OP, 'attendance_days');
    END IF;
    RETURN NEW;
  ELSIF TG_OP = 'DELETE' THEN
    PERFORM public.fn_assert_period_not_frozen(OLD.organization_id, OLD.work_date, TG_OP, 'attendance_days');
    RETURN OLD;
  END IF;
  RETURN NULL;
END;
$$;

CREATE TRIGGER trg_freeze_guard_attendance_days
BEFORE INSERT OR UPDATE OR DELETE ON public.attendance_days
FOR EACH ROW EXECUTE FUNCTION public.fn_freeze_guard_attendance_days();

RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, public
AS $$
DECLARE
  v_conflict_period RECORD;
BEGIN
  IF TG_OP IN ('UPDATE', 'DELETE') THEN

  END IF;

  IF TG_OP IN ('INSERT', 'UPDATE') THEN
    -- Check if any day in the NEW leave range overlaps with a frozen period
    SELECT id, period_name, status INTO v_conflict_period
    FROM public.payroll_periods
    WHERE organization_id = NEW.organization_id
      AND status IN ('FROZEN', 'CLOSED', 'ARCHIVED')
      AND daterange(start_date, end_date, '[]') && daterange(NEW.start_date, NEW.end_date, '[]')
    LIMIT 1;
```

### 3.3 Deterministic JSON Serialization & Cryptographic Staleness Token
Previous reports loosely cited RFC 8785 without acknowledging that PostgreSQL's native `jsonb` type normalizes key order and whitespace in memory, but does not guarantee strict byte-level RFC 8785 wire canonicalization for arbitrary nested arrays, float representations, or non-ASCII characters without custom C extensions.

To achieve genuine deterministic reproducibility and staleness detection without external packages:

1. **Deterministic Representation Protocol:**
   - Numerical aggregates are rounded to explicit fixed precision: `ROUND(val::numeric, 4)::text`.
   - UTC timestamps are formatted identically: `to_char(ts AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US"Z"')`.
   - Arrays are deterministically ordered by their natural compound primary keys before aggregation.
   - Key-value pairs are aggregated using explicit SQL `ORDER BY key`.
   - The final canonical byte payload is hashed using `public.digest(payload::bytea, 'sha256')`.

```sql
CREATE OR REPLACE FUNCTION public.fn_calculate_payroll_snapshot_staleness_token(
  p_payroll_run_id UUID
) RETURNS TEXT
LANGUAGE plpgsql
STABLE
SECURITY DEFINER
SET search_path = pg_catalog, public
AS $$
DECLARE
  v_run_record RECORD;
  v_canonical_json TEXT;
  v_hash_token TEXT;
BEGIN
  SELECT organization_id, payroll_period_id
  INTO v_run_record
  FROM public.payroll_runs
  WHERE id = p_payroll_run_id;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'Payroll run % not found', p_payroll_run_id USING ERRCODE = 'P0002';
  END IF;

  -- Build sorted, canonical JSON string across all line items
  WITH ordered_items AS (
    SELECT
      pli.employee_id::text AS emp_id,
      ROUND(pli.base_salary::numeric, 4)::text AS base_sal,
      ROUND(pli.regular_hours_worked::numeric, 4)::text AS reg_hrs,
      ROUND(pli.overtime_hours_worked::numeric, 4)::text AS ot_hrs,
      ROUND(pli.gross_pay::numeric, 4)::text AS gross,
      ROUND(pli.net_pay::numeric, 4)::text AS net
    FROM public.payroll_line_items pli
    WHERE pli.payroll_run_id = p_payroll_run_id
    ORDER BY pli.employee_id ASC
  ),
  aggregated_json AS (
    SELECT jsonb_agg(
      jsonb_build_object(
        'base_sal', base_sal,
        'emp_id', emp_id,
        'gross', gross,
        'net', net,
        'ot_hrs', ot_hrs,
        'reg_hrs', reg_hrs
      ) ORDER BY emp_id ASC
    ) AS items_array
    FROM ordered_items
  )
  SELECT items_array::text INTO v_canonical_json FROM aggregated_json;

  -- Compute SHA-256 hash over deterministic UTF-8 bytes
  v_hash_token := encode(public.digest(convert_to(COALESCE(v_canonical_json, '[]'), 'UTF8'), 'sha256'), 'hex');

  RETURN v_hash_token;
END;
$$;
```

## 4. FINDING B — TENANT AND ORGANIZATION BOUNDARY ENFORCEMENT

### 4.1 Fail-Closed Session Actor Validation
The flaw identified in A.3.10 was fail-open behavior: when `app.current_user_id` was NULL, the trigger skipped validation. The corrected trigger enforces strict **fail-closed** behavior:

```sql
CREATE OR REPLACE FUNCTION public.fn_assert_record_actor_integrity()
RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, public
AS $$
DECLARE
  v_session_user_id TEXT;
  v_session_org_id TEXT;
BEGIN
  -- Read transactional session GUCs
  v_session_user_id := current_setting('app.current_user_id', true);
  v_session_org_id  := current_setting('app.current_org_id', true);

  -- FAIL-CLOSED ASSERTION: Session context MUST be present
  IF v_session_user_id IS NULL OR v_session_user_id = '' THEN
    RAISE EXCEPTION 'Access denied: Transactional session variable app.current_user_id is unset'
      USING ERRCODE = '42501'; -- insufficient_privilege
  END IF;

  IF v_session_org_id IS NULL OR v_session_org_id = '' THEN
    RAISE EXCEPTION 'Access denied: Transactional session variable app.current_org_id is unset'
      USING ERRCODE = '42501';
  END IF;

  -- TENANT ISOLATION ASSERTION: Row organization MUST match session organization
  IF NEW.organization_id::text <> v_session_org_id THEN
    RAISE EXCEPTION 'Tenant violation: Target organization % does not match session organization %',
      NEW.organization_id, v_session_org_id
      USING ERRCODE = '42501';
  END IF;

  -- AUDIT ACTOR ASSERTION: If created_by is provided on INSERT, it must match session
  IF TG_OP = 'INSERT' THEN
    IF NEW.created_by IS NOT NULL AND NEW.created_by::text <> v_session_user_id THEN
      RAISE EXCEPTION 'Audit spoofing detected: created_by % does not match authenticated user %',
        NEW.created_by, v_session_user_id
        USING ERRCODE = '42501';
    END IF;
    -- Force created_by to match session user
    NEW.created_by := v_session_user_id::uuid;
  END IF;

  RETURN NEW;
END;
$$;
```

### 4.3 Architectural Boundary: Express Gateway vs Database Engine
The security architecture enforces a strict division of responsibility:

```
┌────────────────────────────────────────────────────────────────────────┐
│ EXPRESS API GATEWAY (Untrusted Network Boundary)                      │
│ 1. Terminates TLS & Validates Supabase JWT (RS256 signature, expiry)   │
│ 2. Extracts claims: sub (auth_user_id), org_id, role                   │
│ 3. Verifies Redis active session token & rate limits                   │
│ 4. Acquires pooled PostgreSQL connection from pg-pool                  │
│ 5. Executes: BEGIN;                                                    │
│ 6. Executes: SELECT set_config('app.current_user_id', $1, true),       │
│                     set_config('app.current_org_id', $2, true),        │
│                     set_config('app.current_user_role', $3, true);     │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Parameterized SQL over Pool
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ POSTGRESQL ENGINE (Trusted Enforcement Boundary)                      │
│ 1. Evaluates RLS: organization_id = current_setting('app.current_org_id')│
│ 2. Fires BEFORE Triggers: fn_assert_record_actor_integrity()           │
│ 3. Evaluates Freeze Guards: fn_assert_period_not_frozen()              │
│ 4. Executes Top-Down Locks: L1 (Period) -> L2 (Day) -> L3 (Punch)      │
│ 5. Prohibits Raw Table Owner execution by runtime role (hrms_app_user) │
│ 6. Executes: COMMIT; or ROLLBACK;                                      │
└────────────────────────────────────────────────────────────────────────┘
```

**DML Role Privilege Principle:** The runtime database role `hrms_app_user` possesses `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on tenant operational tables, but **zero administrative permissions** (`NO CREATEDB`, `NO CREATEROLE`, `NO BYPASSRLS`). When `hrms_app_user` evaluates a freeze guard or multi-parent trigger, it executes `SECURITY DEFINER` functions with `search_path = pg_catalog, public`. This guarantees that integrity checks cannot be bypassed or shadowed by malicious search paths.

## 5. FINDING C — LEGACY EMPLOYEE IMPORT SECURITY AND ATOMICITY

### 5.1 Corrected `import_legacy_employee_record()` Function
The implementation below resolves all defects in DEF-11.3:
- Fixes the unassigned `v_user_id` bug by looking up or provisioning the `users` shadow record.
- Enforces the strict 0..1:1 user-to-employee constraint.
- Verifies maintenance role caller authorization.
- Enforces schema search path safety and atomic counter increments.

```sql
CREATE OR REPLACE FUNCTION public.import_legacy_employee_record(
  p_organization_id UUID,
  p_first_name TEXT,
  p_last_name TEXT,
  p_phone_number TEXT,
  p_national_id TEXT,
  p_department_id UUID,
  p_hire_date DATE,
  p_base_salary NUMERIC,
  p_code_prefix TEXT DEFAULT 'EMP'
) RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, public
AS $$
DECLARE
  v_caller_role TEXT;
  v_caller_org TEXT;
  v_user_id UUID;
  v_employee_id UUID;
  v_next_counter INT;
  v_employee_code TEXT;
  v_existing_emp_id UUID;
BEGIN
  -- 1. AUTHORIZATION CHECK: Caller must be MAINTENANCE_ADMIN or SUPER_ADMIN
  v_caller_role := current_setting('app.current_user_role', true);
  v_caller_org  := current_setting('app.current_org_id', true);

  IF v_caller_role NOT IN ('MAINTENANCE_ADMIN', 'SUPER_ADMIN') THEN
    RAISE EXCEPTION 'Unauthorized: Caller role % cannot perform legacy employee import', v_caller_role
      USING ERRCODE = '42501';
  END IF;

  IF v_caller_role <> 'SUPER_ADMIN' AND v_caller_org <> p_organization_id::text THEN
    RAISE EXCEPTION 'Tenant isolation violation: Maintenance caller org % cannot import into org %',
      v_caller_org, p_organization_id
      USING ERRCODE = '42501';
  END IF;

  -- 2. RESOLVE OR PROVISION USER RECORD (Fixes unassigned v_user_id bug)
  SELECT id INTO v_user_id
  FROM public.users
  WHERE organization_id = p_organization_id
    AND phone_number = p_phone_number;

  IF v_user_id IS NULL THEN
    -- Provision shadow user record for legacy employee
    INSERT INTO public.users (
      organization_id,
      phone_number,
      role,
      status,
      created_at,
      updated_at
    ) VALUES (
      p_organization_id,
      p_phone_number,
      'EMPLOYEE',
      'INVITED',
      now(),
      now()
    ) RETURNING id INTO v_user_id;
  END IF;

  -- 3. ENFORCE 0..1:1 USER-TO-EMPLOYEE CONSTRAINT
  SELECT id INTO v_existing_emp_id
  FROM public.employees
  WHERE user_id = v_user_id
    AND organization_id = p_organization_id;

  IF v_existing_emp_id IS NOT NULL THEN
    RAISE EXCEPTION 'Integrity violation: User % is already mapped to employee %',
      v_user_id, v_existing_emp_id
      USING ERRCODE = '23505'; -- unique_violation
  END IF;

  -- 4. ATOMIC COUNTER ALLOCATION & OVERFLOW PREVENTION
  -- Acquire row lock on organization sequence row
  SELECT last_value + 1 INTO v_next_counter
  FROM public.organization_sequences
  WHERE organization_id = p_organization_id
    AND sequence_type = 'EMPLOYEE_CODE'
  FOR UPDATE;

  IF NOT FOUND THEN
    -- Initialize sequence if missing
    INSERT INTO public.organization_sequences (organization_id, sequence_type, last_value)
    VALUES (p_organization_id, 'EMPLOYEE_CODE', 1)
    RETURNING last_value INTO v_next_counter;
  ELSE
    -- Check 6-digit counter overflow ceiling (999,999)
    IF v_next_counter > 999999 THEN
      RAISE EXCEPTION 'Counter overflow: Maximum employee code ceiling (999999) reached for org %',
        p_organization_id
        USING ERRCODE = '22003'; -- numeric_value_out_of_range
    END IF;

    UPDATE public.organization_sequences
    SET last_value = v_next_counter, updated_at = now()
    WHERE organization_id = p_organization_id
      AND sequence_type = 'EMPLOYEE_CODE';
  END IF;

  -- Format deterministic code: EMP000001
  v_employee_code := p_code_prefix || lpad(v_next_counter::text, 6, '0');

  -- 5. ATOMIC INSERT INTO EMPLOYEES
  INSERT INTO public.employees (
    organization_id,
    user_id,
    employee_code,
    first_name,
    last_name,
    national_id,
    department_id,
    hire_date,
    employment_status,
    created_at,
    updated_at
  ) VALUES (
    p_organization_id,
    v_user_id,
    v_employee_code,
    p_first_name,
    p_last_name,
    p_national_id,
    p_department_id,
    p_hire_date,
    'ACTIVE',
    now(),
    now()
  ) RETURNING id INTO v_employee_id;

  -- 6. ATOMIC INITIAL SALARY ASSIGNMENT
  IF p_base_salary IS NOT NULL AND p_base_salary > 0 THEN
    INSERT INTO public.salary_assignments (
      organization_id,
      employee_id,
      base_salary,
      effective_from,
      created_at
    ) VALUES (
      p_organization_id,
      v_employee_id,
      p_base_salary,
      p_hire_date,
      now()
    );
  END IF;

  RETURN jsonb_build_object(
    'status', 'SUCCESS',
    'employee_id', v_employee_id,
    'user_id', v_user_id,
    'employee_code', v_employee_code
  );
END;
$$;
```

### 5.2 FORCE ROW LEVEL SECURITY & Table Owner Isolation
In PostgreSQL, `ENABLE ROW LEVEL SECURITY` causes RLS policies to apply to all normal roles, but **not to the table owner** (`hrms_schema_owner`) or superusers. Conversely, `FORCE ROW LEVEL SECURITY` applies RLS policies to the table owner as well.

- **The Bootstrap Conundrum:** If `FORCE RLS` were applied to `users`, then when `hrms_schema_owner` executes `resolve_user_auth_context()` to find an incoming user's tenant ID, the query would execute under RLS. But because the tenant GUC (`app.current_org_id`) has not yet been set, the RLS policy would evaluate to `FALSE`, returning 0 rows and bricking login bootstrap.
- **Architectural Policy:**
  - `organizations` and `users`: `ENABLE ROW LEVEL SECURITY` (WITHOUT `FORCE RLS`). This permits `SECURITY DEFINER` bootstrap functions owned by `hrms_schema_owner` to look up authentication credentials before tenant context is set.
  - All operational tables (`attendance_days`, `attendance_punches`, `payroll_runs`, etc.): `FORCE ROW LEVEL SECURITY`. This guarantees that even if a table owner connection executes operational queries, tenant isolation remains strictly enforced.

### 5.3 Schema Creation Revocation & Search Path Defense
To prevent unprivileged roles from creating malicious functions or operators that could hijack `SECURITY DEFINER` execution:
1. `REVOKE CREATE ON SCHEMA public FROM PUBLIC;`
2. `REVOKE ALL ON DATABASE hrms_db FROM PUBLIC;`
3. All stored procedures explicitly specify: `SET search_path = pg_catalog, public;`.

## 6. FINDING D — PAYROLL LOCKING HIERARCHY AND ENGINE EXECUTION ORDER

### 6.1 The PostgreSQL Engine Reality: Lock Acquisition Before Trigger Execution
In PostgreSQL, the execution mechanics of an update query are as follows:

```
Step 1: Application issues: UPDATE attendance_days SET total_hours = 8 WHERE id = $1;
Step 2: Engine scans index, locates heap tuple.
Step 3: Engine IMMEDIATELY acquires Exclusive Tuple Lock (FOR UPDATE) on the attendance_days row!
Step 4: Engine invokes BEFORE UPDATE trigger: fn_freeze_guard_attendance_days().
Step 5: Inside trigger, code attempts: SELECT 1 FROM payroll_periods WHERE ... FOR SHARE;
```

**The Fatal Lock Inversion Flaw:**
If a transaction attempts to acquire parent locks *inside* a `BEFORE` trigger on a child table, the engine has **already locked the child row ($L_2$) before the trigger requests the parent lock ($L_1$)**. 
If a concurrent payroll run transaction executes in top-down order ($L_1 \to L_2$):
- **Tx1 (Child Update via Trigger Lock):** Holds $L_2$ lock, requests $L_1$ lock.
- **Tx2 (Payroll Run Freeze):** Holds $L_1$ lock, requests $L_2$ lock.
- **Result:** **Instant Deadlock Cycle ($L_2 \to L_1$ vs $L_1 \to L_2$)**. PostgreSQL's deadlock detector triggers after `deadlock_timeout` (default 1s) and aborts one of the transactions.

### 6.2 Top-Down Hierarchical Locking Protocol ($L_1 \prec L_2 \prec L_3 \prec L_4$)
To eliminate deadlocks mathematically, all transactions modifying attendance or payroll data MUST acquire locks strictly in top-down order at the **transaction entry level** (application handler, gateway, or workflow procedure), **never** relying on child triggers to retroactively acquire parent locks.

$$\text{Lock Order: } L_1 (\text{payroll\_periods}) \prec L_2 (\text{attendance\_days}) \prec L_3 (\text{punches/allocations}) \prec L_4 (\text{audit\_logs})$$

- **$L_1$ (`payroll_periods`):**
  - Acquired `FOR SHARE` by any transaction performing operational mutations (punches, day edits, leave, overtime).
  - Acquired `FOR UPDATE` exclusively by payroll calculation and freeze transactions.
- **$L_2$ (`attendance_days`):** Acquired `FOR UPDATE` by day edits or punch mutations.
- **$L_3$ (`attendance_punches`, `overtime_allocations`):** Acquired `FOR UPDATE` by child edits.
- **$L_4$ (`attendance_audit_logs`):** Append-only `INSERT`.

**The Role of Triggers:** The `BEFORE` triggers act as **read-only state validation guards** that verify status (`status NOT IN ('FROZEN', 'CLOSED')`), but **never execute `FOR SHARE` or `FOR UPDATE` locking**.

## 7. FINDING E — SESSION INITIALIZATION AND CONTEXT RESOLUTION

### 7.1 Reassessment of `resolve_user_auth_context()` under RLS
To resolve DEF-11.5, the table-level RLS settings and bootstrap lookup are defined as:

### 7.2 Express Connection Pool Lifecycle & Transaction Scoping
To prevent connection state leakage across pooled requests in Node.js / Express:

```typescript
import { Pool, PoolClient } from 'pg';

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 50,
  idleTimeoutMillis: 30000,
});

export async function executeTransactionalSession<T>(
  userId: string,
  orgId: string,
  userRole: string,
  callback: (client: PoolClient) => Promise<T>
): Promise<T> {
  const client = await pool.connect();
  try {
    // 1. Begin atomic transaction
    await client.query('BEGIN');

    // 2. Set LOCAL transaction-scoped GUCs (3rd argument `true` scopes strictly to transaction)
    await client.query(
      `SELECT
         set_config('app.current_user_id', $1, true),
         set_config('app.current_org_id', $2, true),
         set_config('app.current_user_role', $3, true)`,
      [userId, orgId, userRole]
    );

    // 3. Execute business logic
    const result = await callback(client);

    // 4. Commit transaction (automatically clears transaction-scoped GUCs)
    await client.query('COMMIT');
    return result;
  } catch (error) {
    // 5. Rollback on failure
    await client.query('ROLLBACK');
    throw error;
  } finally {
    // 6. Defensive connection sanitization before returning to pool
    try {
      await client.query('DISCARD SEQUENCES; RESET ALL;');
    } catch (resetErr) {
      // If reset fails, destroy connection completely
      client.release(true);
      return;
    }
    client.release();
  }
}
```

### 7.3 Redis Session Cache Limitations & Invalidation
- **Cache Payload:** `session:{auth_user_id}` stores `{ user_id, org_id, role, status }` with TTL = 300s (5 minutes).
- **Cache Invalidation:** Any administrative mutation modifying `users.status`, `users.role`, or `organizations.status` emits a Redis `DEL session:{auth_user_id}` command.
- **Split-Brain Mitigation:** If Redis is partitioned or unavailable, the Express gateway falls back to executing `resolve_user_auth_context()` directly on PostgreSQL. If a user is deactivated in PostgreSQL, the database trigger on `users` raises `SQLSTATE 42501` immediately, rejecting mutations even if a stale Redis token exists.

## 9. REMAINING ARCHITECTURAL CONTRADICTIONS & DEPENDENCIES

1. **Client-Side vs Database-Side $L_1$ Lock Enforcement:**
   Top-down hierarchical locking ($L_1 \prec L_2 \prec L_3 \prec L_4$) eliminates deadlocks, but relies on the **application layer** (Express gateway, Celery worker) to consistently issue `SELECT ... FROM payroll_periods FOR SHARE` as the first statement of every mutation transaction. If a developer introduces an ad-hoc query that executes an un-guarded `UPDATE attendance_days`, the database engine will lock $L_2$ first, reintroducing deadlock risk against a concurrent payroll freeze.
   - *Mitigation in Phase B:* Wrap all attendance mutations inside database stored procedures (e.g., `public.record_attendance_punch()`, `public.update_attendance_day()`) that enforce $L_1$ acquisition internally.

2. **Midnight Cross-Day Shifts:**
   A night shift starting at 22:00 on Day 1 and ending at 06:00 on Day 2 spans two calendar dates. `attendance_days` represents a single calendar working date.
   - *Architectural Rule:* The working date of a punch is determined by the `shift_assignments.assigned_date` of the shift to which the punch is attributed, not by the raw UTC timestamp of the punch.
